# C156 代码导览

这份导览面向第一次接手项目的合作者：先了解内容如何从页面进入 SQLite，再按功能找到文件和测试。当前的核心是虚拟目录、文档和正文修订，CLI 与本地网页共用同一个内容服务。

## 先读哪些文件

第一次阅读只需沿下面五个文件走一遍，不必逐行看完大文件：

1. [core/models.py](../src/core/models.py)：看 `ContentScope`、`NodeSnapshot`、`DocumentSnapshot`，认识输入范围和返回数据。
2. [storage/schema.py](../src/storage/schema.py)：看 `objects`、`entries`、`document_revisions` 三张表，理解身份、目录位置、正文为什么分开存。
3. [services/content.py](../src/services/content.py)：先看 `read_document()` 和 `save_document()`，理解业务操作；遇到辅助函数再按本文的分区索引查。
4. [storage/database.py](../src/storage/database.py)：看 `transaction()`，理解一次操作在哪里开始、提交或回滚。
5. [storage/repository.py](../src/storage/repository.py)：跳到 `Repository` 类，只看 `get_revision()`、`insert_revision()`、`update_entry()`，对照保存操作的 SQL。

网页开发再沿 [static/app.js](../src/web/static/app.js) 的 `saveDocument()` → [static/client.js](../src/web/static/client.js) 的 `Client.saveDocument()` → [web/api.py](../src/web/api.py) 的 `API.dispatch()` 阅读。终端开发从 [cli/commands.py](../src/cli/commands.py) 的 `command_edit()` 开始。

旧数据迁移、终端键盘编辑和第三方压缩库都可以等涉及相应功能时再读。详细业务契约见 [内核设计](superpowers/specs/2026-09-30-single-sqlite-content-kernel-design.md)，具体页面接线见 [工作台开发](工作台开发.md)。

## 核心结构

```text
浏览器 → web API ─┐
                 ├→ ContentService → Repository → SQLite
终端   → cli ────┘         │              ↑
                           └→ Database ───┘
                              同一次操作的连接与事务

core 提供纯数据和规则；editor 只编辑内存正文，由 cli 决定保存。
storage management 和 legacy 是显式管理入口，不在日常正文读写链路中。
```

SQLite 文件在宿主机磁盘上；小说章节和设定文档的目录关系在数据库里，不对应磁盘目录。改名或移动主要修改目录条目，不搬动宿主机文件。

| 表或数据类型 | 管什么 | 例子 |
| --- | --- | --- |
| `objects` | 对象的稳定 ID、类型和所属工作区 | 第一章是一个 document，改名后 ID 不变 |
| `entries` | 分支内的名称、父目录、排序、metadata、删除状态和当前正文指针 | 第一章位于作品目录，当前指向修订 R2 |
| `document_revisions` | 不可变的全文正文修订及父修订 | R1 和 R2 分别保存修改前后的正文 |
| `workspaces`、`branches` | 内容所属工作区和分支 | 当前默认工作区与 main 分支 |
| `legacy_imports` | 旧数据来源摘要及迁移报告 | 识别同一批旧数据的重复导入 |
| `ContentScope` | 本次调用的工作区、分支和访问根 | 网页只能访问服务端固定的根范围 |
| `NodeSnapshot`、`DocumentSnapshot` | 返回给入口的只读数据 | 名称、路径、版本；文档还携带正文和修订 ID |

`entry.version` 检测结构或 metadata 冲突，`revision_id` 检测正文冲突，`subtree_token` 检测确认删除后子树是否变化。访问根检查不是用户身份认证；表里存在 branches 也不代表已经交付分支切换或作品级提交。

## 跟一次保存走完整条链路

1. `app.js` 调用 `EditorState.beginSave()`，捕获此刻的正文和 `expected_revision_id`。之后继续输入仍留在草稿里。
2. `Client.saveDocument()` 发送 `PUT /api/document`；`http.py` 做传输校验，`API.dispatch()` 做字段校验。
3. `ContentService.save_document()` 通过 `Database.transaction(write=True)` 开启写事务，校验访问范围、类型和基础修订。
4. 基础修订过旧时返回 `Conflict`，不覆盖正文。基础有效且内容相同时不新增修订；有变化时 `Repository.insert_revision()` 保存全文，再用 `update_entry()` 条件更新当前指针与条目版本。
5. 成功提交后返回 `DocumentSnapshot`，序列化为 JSON；`EditorState.saveSucceeded()` 更新保存基础，保留请求期间的新输入。失败则保留草稿和原基础修订。

终端走同一个保存方法：CLI 先读取，Editor 在事务外编辑并返回结果，CLI 再保存。人输入、确认和手动合并时不一直持有数据库事务。

## 后续精简的边界

如果目标是减少维护负担，可优先评估旧迁移流程和弃用兼容入口是否还需要长期保留。删除前须确认旧数据转换已经完成、调用方已迁移，并同步对应入口、导出、测试和文档；`src/file/bootstrap.py` 仍然调用管理入口，不能只删一侧。

拆分大文件能让职责更清楚，但不等于减少总代码量。可考虑将 `legacy.py` 的扫描与迁移协调分开，将 `repository.py` 的管理核对与运行 DAO 分开；这些是整理方向，本次仅补充导览。

精简时保留以下系统约束：

- CLI 和 Web 经由 ContentService 操作内容；服务执行业务校验，Repository 执行 SQL，Database 管理连接与事务。
- 普通启动不隐式创建、导入或修复数据库；管理操作和演示初始化显式执行。
- 当前访问范围、修订冲突检查、失败草稿保留和事务原子性不能因用户少而省略。
- 正文修订保存全文且不可变；历史浏览、恢复、认证权限、实时协作和作品级版本管理尚未交付，见 [架构分层](架构分层.md#当前实现范围)。
