## 已确认的升级路线

[D12](决策记录.md)：停止全部写入后备份，在原库事务升级，使用标准 Alembic 管理迁移。复制新库再切换作为比较过的备选，不是本阶段采用的路线。

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 停写并备份后原库事务升级 | 保持部署路径，复用现有运行库 | 需要维护窗口、升级失败回滚和版本校验 |
| 复制为新库、验证后切换 | 验证通过前保留原库 | 需要定义切换原子性、WAL 处理和部署恢复 |

升级由显式管理命令执行，启动只验证；不在账号使用站点时偷偷变更 schema。升级必须保留已有身份、正文、修订关系和权限数据，不能以重新初始化代替。

原库事务升级：维护窗口先阻止所有写入口（包括 CLI 和后台命令），再备份已停写的状态；在单事务内执行受支持的 schema/数据变更、核对不变量并更新版本记录；成功后启动新版本，事务失败则回滚并保持维护状态。备份不应早于最后一笔允许写入，否则用它恢复可能丢失中间的新稿。

现有备份函数只接受 `SCHEMA_VERSION` 指定的版本。升级前备份需要使用能读取源版本的工具，不能假定新应用的备份命令已经兼容旧库。版本支持范围、部署衔接与失败回退仍待具体设计。

## Alembic 接入待细化

Alembic 用 SQLAlchemy 作为迁移连接与操作引擎，并通过 `alembic_version` 记录迁移位置。[官方教程](https://alembic.sqlalchemy.org/en/latest/tutorial.html)

建议迁移环境使用这些标准机制，现有运行时的 sqlite3、Repository 和 UoW 保持现有职责；采用 Alembic 不要求将内容服务整体改为 ORM。具体目录、依赖版本和管理命令在规格中确定，本次未安装依赖或生成迁移代码。

### 已确认的版本依据

[D13](决策记录.md)：Alembic revision 是接管后数据库版本的唯一依据。应用运行打开、备份和管理入口据此校验，不再维护独立递增的 `user_version` 应用协议。运行校验可以通过现有 sqlite3 读取版本记录，不必在运行打开时执行迁移。

旧 `user_version` 用于识别尚未接管的源库；迁移后必须确保旧应用不能误把新库当作原协议继续写入，具体兼容阻断方式在规格中明确。如保留旧应用拒绝识别的标记，它仅用于兼容阻断，不成为第二套迁移版本记录。

### 已确认的新建、接管和导入边界

[D14](决策记录.md)：三种入口使用同一份 Alembic schema 来源：

| 入口 | 流程职责 |
| --- | --- |
| 新建空库 | 从 Alembic base 升级至目标 revision，管理服务再创建初始工作区和目录等业务数据 |
| 接管现有统一库 | 核验现有协议 2 的真实 schema 和数据约束，登记对应的基线 revision，再执行后续迁移 |
| 旧单容器导入 | 在新的临时目标库中通过迁移链创建目标 schema，再执行现有导入协调、核对和不覆盖发布 |

此方案将建表和 schema 演进统一到迁移链；初始化与导入模块保留各自的数据和生命周期职责。现有 `create_schema` 不再独立维护一份随版本更新的最新建表脚本；历史迁移脚本也不能通过导入未来会变化的“最新 schema”函数来建表。

### 接管与完整性要求

- 已有协议 2 的库先核验真实 schema 和数据约束，再登记受支持的 Alembic 基线；不能只凭 `user_version=2` 盲目 stamp，更不能 stamp 最新 head 跳过实际迁移。
- 新建库、旧容器导入与现有 `create_schema` 的职责按 D14 收敛；迁移目录和调用契约在规格中细化。
- SQLite 的 Python 驱动存在 DDL 不自动开启事务的模式。迁移环境必须明确开启真实事务，并用实际失败回滚验证 DDL、数据及 Alembic 版本记录一起回滚；不能把模板里的事务上下文当作已经成立的保证。[SQLite 事务说明](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#transactions-with-sqlite-and-the-sqlite3-driver)
- 如需 SQLite batch 重建表，迁移脚本必须核对外键、CHECK、部分唯一索引及现有不可变触发器。复合和自引用外键的处理需要按实际 schema 设计，不依赖自动生成脚本猜测。[Alembic SQLite batch](https://alembic.sqlalchemy.org/en/latest/batch.html)
- 迁移事务失败回滚、迁移成功但新应用启动失败、重新开放写入后出现问题，是不同的恢复情形。不得在已产生新稿后静默覆盖为升级前备份；schema downgrade 的支持范围另行设计。
