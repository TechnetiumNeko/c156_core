# 项目分层与入口

C156 的目标是供用户共同创作和阅读内容的网站。抽象文件系统负责组织内容；CLI 是当前便于开发和验证的终端入口，网页是计划中的用户入口。CLI 的 `ls`、`cat`、`edit` 等命令只是终端交互方式，不定义网页 API，也不是内容对象自身的接口。

## 目标关系

```text
CLI（当前入口） ──┐
                 ├──→ 内容服务 ──→ 抽象文件系统 ──→ 存储实现
网页（计划入口）──┘          └──→ 修订与版本管理（计划）
```

- **内容内核**：管理文件对象的稳定 ID、类型、目录关系、文档正文及后续的引用等内容关系。实时协作管理正在编辑的共享草稿，修订与版本管理记录阶段成果及其分叉；这些能力尚未实现，具体存储方案也未确定。
- **内容服务**：面向入口提供列目录、读取、创建、保存等操作，并在有用户系统后统一执行身份与权限检查。它是计划中的共享边界，当前代码尚未形成独立的服务层。
- **入口**：CLI 和网页分别处理各自的输入与展示，调用相同的内容服务。网页不解析命令字符串，不调用 `CLI.execute()`，也不启动终端编辑器。
- **存储实现**：当前原型把虚拟目录映射到 `data` 中的真实目录，并使用 SQLite 文件保存对象数据。这个映射不决定上层入口如何交互。

例如，CLI 的 `ls` 与网页中的目录浏览都需要“列出目录内容”；CLI 的 `cat` 与网页中的文档阅读都需要“读取文档”。CLI 的 `edit` 包含终端交互，网页编辑则应分别调用读取和保存操作。两种入口共享内容操作，而不共享终端命令。

## 共享草稿与阶段版本

项目用于朋友之间共同创作架空小说，章节、人物档案和世界观设定需要一起维护。协作与版本管理按以下方式分工：短时间尺度的日常编辑参考实时协作文档，默认同步向前推进；较大时间尺度的创作成果参考 Git 的提交、分支和合并。

| 层次 | 行为 | 用途 |
| --- | --- | --- |
| 共享草稿 | 同一分支内的作者实时共同编辑，自动同步和保存 | 日常写作，修改标点或几个字无需手动提交 |
| 草稿恢复记录 | 自动保存可恢复状态，编辑历史可按时间或会话合并展示 | 恢复误删内容和未完成的工作 |
| 阶段提交 | 作者主动确认一组修改，填写提交说明，形成不可变快照 | 记录“完成第三章”“统一人物背景”等有意义的成果 |
| 里程碑与发布 | 标记或发布一个已确认的提交 | 固定“第一卷初稿”“连载版”等阅读和分享版本 |

是否创建阶段提交由作者对成果的确认决定，同时考虑时间尺度和修改的语义。自动保存和细小的同步事件无需各自生成正式提交；主要版本时间线展示阶段成果，草稿恢复历史提供更细的回溯。同步日志的合并存储与正文历史的保留要求需要分别设计。

### 分支与合并的范围

- 分支覆盖整个作品／工作区，一次提交可以同时包含章节、人物设定等多篇文档。
- 每个分支拥有自己的共享草稿；实时同步以“工作区＋分支＋文档”为范围，不同分支独立编辑。
- 从阶段提交创建分支，探索不同改稿方案；分支内继续使用实时协作。
- 提交需要捕获服务器已确认的一致状态，记录文档修订、目录结构及引用的媒体版本。后续编辑继续进入草稿，已创建的提交保持不变。
- 合并请求比较共同祖先、目标分支和来源分支的版本，支持人工处理冲突并由有审核权的人确认。文本能够自动合并时，仍需审核剧情和设定的一致性。
- 合并前需要处理目标分支的未提交草稿，并协调正在编辑的客户端，避免覆盖现有工作。
- 恢复旧成果通过创建新提交保留操作经过；发布与草稿编辑分别管理，继续写作不改变已发布的版本。

### 参考现有协作库

共享文档功能优先参考和复用成熟的实时协作库及编辑器集成，例如 [Yjs](https://docs.yjs.dev/)。可以利用已有库处理并发编辑、同步和协作状态，编辑器、传输方式及服务端接入方案在实现时选定。

项目自身负责工作区与分支的隔离、身份和权限检查、协作状态的持久化，以及阶段快照、提交关系、审核和合并。实时编辑的自动同步与跨分支的成果合并分别处理；协作库的自动收敛不能代替剧情和设定审核。

## 当前实现范围

目前已有抽象文件记录、目录和文档的 SQLite 存储，以及直接调用这些存储对象的 CLI 和测试用终端编辑器。网页入口、共享内容服务、用户认证与授权、实时协作、修订与版本管理均未实现。以上描述的是目标设计，不表示现有 CLI 已经通过内容服务访问存储或具备协作与版本能力。
